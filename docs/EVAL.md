# 评测报告 · gaokao-audit v1（Plan 1）

> 跑法：`py eval/run_eval.py --n 50` · 本报告数字由该命令实跑产出，**不是设计目标**。

## 一、为什么用「错误注入」而不是"人工标注的标准答案"

校验器没法拿"标准答案"来衡量 —— 但可以拿**自己塞进去的已知错误**来衡量：

```
干净的表 ──注入 N 个已知错误──→ 喂给系统 ──→ 系统报出 M 条问题
                                              ↓
                                  抓到了几个？误报了几个？
```

四类注入，每一类都对应**真实产品犯过的错**：

| 注入类 | 干了什么 | 期望被哪条检查抓到 |
|---|---|---|
| `year` | 把位次换成用**另一年**的表算出来的 | `rank_year_mismatch` |
| `number` | 把声称的最低分改动 ±30 分 | `line_mismatch` |
| `tier` | 换成**考生够不着**的组的真实数据，再标"稳" | `tier_inconsistent` |
| `subject` | 把考生选科换成不满足要求的组合 | `subject_not_allowed` |

## 二、实测数字

```
样本：60 条志愿 · 每类注入 50 条（合计 200 个已知错误）
──────────────────────────────────────────────
干净表基线误报         : 0
检出率 recall          : 0.905
精确率 precision       : 0.963
    year     recall = 0.980
    number   recall = 1.000
    tier     recall = 1.000
    subject  recall = 0.640
```

**样本量声明**：每类 50 条、合计 200 个注入错误。`run_eval` 内置门槛
（`SAMPLE_FLOOR = 50`），低于它会在报告里打警告 —— 项目① 栽在"18 道题撑不起结论"，
这里不重蹈。

**precision 0.963 的口径**：分母**只统计可注入的那四类 finding**。
理由：一次注入只制造**一个**已知错误，但审计可能**连带**报出同一行上的其它真实不一致
（例如 `number` 注入改了分数没改位次，会连带产生一条真实的 `rank_mismatch`）。那些是**真问题、不是误报**。
把连带项算进分母会系统性压低精确率 —— 这一点是**独立评审提出来的**，修之前精确率是 0.762。
干净表上的基线误报是 **0**，那才是真正的"没有误报"。

## 四、🔴 已知抓不到 / 效果较弱的（必须主动说）

### 1. `bc5` 这一类：**填报规则常识**，本项目完全不覆盖

「平行志愿能填几个专业组」这类信息，**既不在一分一段表、投档线，也不在招生计划里** ——
它是一个**省份级的政策常量**。

要覆盖它，需要额外维护一份「各省规则常量表」并逐年核对。这**明确不在本版本范围内**
（spec §2 非目标：只做数据与逻辑的自洽性检查，不做政策解读）。

### 2. `subject` 类检出率只有 **0.640**

原因不是解析出错，而是**这一类错误有一部分在定义上就无法伪造**：
真实数据里有相当比例的选科要求是「**不限**」（2025 年尤其多）——
对「不限」的组，**无论怎么改考生选科，它都该被满足**，所以这些组不可能产生"选科不满足"的错误。
它们被计入了分母，把检出率拉了下来。

**这是指标口径问题，不是系统缺陷** —— 但如果只看那个 0.640 会误判。诚实写法是把原因讲出来，
而不是换个更有利的分母。

### 3. 数据覆盖的边界（不是模型问题，是数据集本身的洞）

| 检查 | 可用年份 |
|---|---|
| 位次换算 | 2022 / 2023 / 2024 / 2025 |
| 投档线核对、分档逻辑 | **只有 2022 / 2025**（2023 整张缺失、2024 只有专科批） |
| 选科能不能报 | **只有 2025**（`enrollment_plan.major_group` 只在这一年非空） |

详见 [`data-schema.md`](data-schema.md)。

### 4. 只做**自洽性**检查，不做**价值判断**

系统不会回答"你该不该报这个专业"、"这个专业前景如何"。那是价值取舍，没有 ground truth。

## 四点五、一个**用数字换数字**的取舍（记在这里，因为它改变了上面那组数）

把演示流程真跑一遍（`scripts/make_demo.py`）时，报告里冒出 3 条 `rank_mismatch`：
位次差 1076 / 10 / 101 —— **它们全是假阳性**。

根因不是代码错，是**我原来把位次比对的容差写死成 5 名**，等于假设"同一个分数只有一个人"。
而投档表里的「最低位次」是**投档最低排位**（最后一个被录取者的名次），
`rank_of()` 给的是**该分数的段末位** —— 同一个分数有几百上千人，两者合法地差出几百名。

修法：**容差 = max(固定下限, 该分数段的段内人数)**。段内人数就是"同分最多能差多少"的物理上界，
所以这是**有依据的**，不是"把阈值调大让它别报"。

**代价（照实写）**：

| | 改之前 | 改之后 |
|---|---|---|
| 干净表基线误报 | 0 | 0 |
| 全体 recall | 0.910 | **0.905** |
| `year` 类 recall | 1.000 | **0.980** |

**用 1 个漏报换掉了整类假阳性。** 而且注意：**这个取舍是靠"把演示真跑一遍"发现的，
不是靠单元测试** —— 单元测试里的"干净表"是用 `rank_of()` 自己造出来的，
位次天然自洽，永远碰不到这个矛盾。这是一个很典型的"测试自己造数据 → 测不出真实数据的问题"。

## 五、实施期间修掉的四个"会让结论失真"的问题

记录下来，因为它们比数字本身更能说明"证据是怎么来的"：

1. **`major_group` 跨表写法不同**（`（206）` vs `206`）—— 两张表 JOIN **恒为 0 行**，
   选科检查会**静默查不到任何要求**。归一化后 JOIN 变 1417 行。
2. **2025 的 `subject_req` 与其它年份格式不同**（丢了"首选X"前缀）——
   只认旧格式的解析器会把 2025 **一律判为"满足"**，检查永远报不出问题。
3. **评测用的"干净表"其实不干净**（考生位次设成垫底值、所有组标"稳"）——
   `tier` 的 recall 一度是 **1.0**，但那是**假阳性撑出来的**，等于没测。
4. **投档线查询漏了科类**（独立评审发现）—— 同校同组号，物理类与历史类的分数线是两回事，
   实测库里有 **6 组**这样的组合。漏掉 `category` 会取到另一个科类的行，**不报错，只让结论翻盘**
   （够得着的组被误报成"够不着"）。

**共同点：四个都不会报错，只会让结果看起来"更好"或"更理直气壮"。** 所以它们只有靠写测试 + 对照真实数据 + 独立评审才发现。
