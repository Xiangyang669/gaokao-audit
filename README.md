# gaokao-audit · 高考志愿方案审计器

一个面向高考志愿的 Agent：**能审一份方案对不对，也能生成一份方案 —— 而且生成完会被它自己审一遍。**

## 它做两件事，而且这两件事是连着的

```
  ① 审计：给一份填好的志愿表 + 一个提问
        → 检查表里的数据与逻辑是否自洽，返回带证据的问题清单

  ② 推荐：给一位考生（分数 / 位次 / 选科 / 偏好）
        → 确定性筛选 → LLM 排序组合并说明理由 → 出一份冲稳保分布

  ③ 闭环：② 生成出来的方案，自动走一遍 ①          ← 这是两件事接在一起的地方
```

**它的立场是「能证明」**：审一份表，答案对不对**有客观判据**（数据库里的真实投档线就是答案）；
生成一份方案，好不好**也能回测**（用参照年生成、用真实录取结果检验）。
**两件事都有数字，两个数字都在下面。**

## 实测数字

**审计**（错误注入 + 公开横评记录的真实 badcase）：

| 指标 | 值 |
|---|---|
| 检出率 recall | **0.905** |
| 精确率 precision | **0.963** |
| 干净表基线误报 | **0** |

**推荐**（回测：参照年 2022 → 检验年 2025，40 个考生视角）：

| 指标 | 值 |
|---|---|
| 录取率（推荐的条目里他能上几个） | **0.355** |
| 浪费位次 P50 / P90 | 14443 / 30543 |

两个数字的完整说明、以及**已知抓不到的类别**，分别在
[`docs/EVAL.md`](docs/EVAL.md) 与 [`docs/BACKTEST.md`](docs/BACKTEST.md)。

> 推荐那个数字低，根因不是模型不行，是**用单一年份当参照这件事本身不够** ——
> 2022→2025 各专业组录取位次整体漂移，而 2023/2024 的数据恰好缺失。
> 那一份里也写明了**没有跑对照基线**（所以还说不清模型贡献了什么）。

## 审计：它检查什么

| 检查 | 抓什么 |
|---|---|
| `rank_conversion` | 位次是不是用**别的年份**的一分一段表算的（能指名道姓说是哪一年） |
| `admission_line` | 表里声称的投档线跟真实值对不上 |
| `tier_logic` | 标着"稳/保"，但位次其实**够不着** |
| `subject_plan` | 考生选科不满足该专业组的要求 |
| `adjacent_group_verify` | （追加）判"够不着"时，同校相邻组是否够得着 —— **可能是组号读错了** |

前四个是**纯规则、零 LLM**。全系统只有 5 处模型调用（截图解析 / 意图分类 / supervisor / 报告 / 推荐组合），
其中 supervisor **在无异常时根本不调用**。

**它长这样**（浏览器里）：

```
上传一张志愿表截图 ──→ ① 多模态解析出结构化的表
                    ──→ ② 「我读到 N 条，对吗？」人工核对一遍     ← 输入错了，后面全是错的
                    ──→ ③ 跑那几路检查
                    ──→ ④ 出报告：每条问题带声称值 / 真实值 / 证据
```

## 推荐：闭环怎么走

```
考生信息 → 确定性筛选（零 LLM，位次带 + 选科）→ LLM 在候选里挑与排、逐条说理由
                                                        │
                                                        ▼
                              生成的方案喂回审计器自审 —— 干净生成应为 0 发现
```

**自审那一步是这两个功能接在一起的地方**，也有对照测试：
守规矩生成 → 0 发现；故意把档位标错 → **被自己的审计器抓到**。

推荐**只能在已筛出的候选里挑**：筛选是纯规则（位次带 + 选科），模型不许发明候选之外的院校，
空理由不算数，没候选时**根本不调模型**。

## 怎么跑

```bash
py scripts/build_db.py      # CSV → SQLite（库已在仓库里，这步可跳过）
py -m pytest -q             # 170 个测试，全程离线（走缓存）

cp .env.example .env        # 填 DEEPSEEK_API_KEY
docker compose up -d         # → http://localhost:8000
cd frontend && npm install && npm run dev
```

> **演示路径零 API 花费**：响应缓存被打进了镜像，
> 所以「载入示例 → 开始审计」这条路**全程不调用模型**；只有上传自己的新截图才会真调。

## 数据

- 来源：`Gaokao-Compass-11M`（Hugging Face），经 `hf-mirror.com` 下载
- 范围：**广东省 · 本科批**

> ⚠️ **数据覆盖不完整，且这是已知边界**：2023 年本科批录取数据整张缺失、2024 年只有专科批，
> 2021 年一分一段表的科类/批次字段全空，投档线相关的检查实际只覆盖 2022 与 2025。
> 各检查项**实际可用的年份**见 [`docs/data-schema.md`](docs/data-schema.md)。

## 已知边界（主动说）

- **数据只覆盖广东 + 有限年份**；长尾院校（地方/职业院校）必有缺口
- **不做价值判断** —— 不回答"你该不该报这个专业"
- **护栏是进程内内存 + 一把锁** —— 多实例部署要换成共享存储
- **推荐的回测参照深度只有 1 年**，且无对照基线

```

├── checks/        四个确定性检查（+ 一个追加检查）—— 零 LLM

├── pipeline/      截图解析 / 意图分类 / supervisor / 报告 / LangGraph 编排

eval/              错误注入 + 真实 badcase + 评测 harness + 回测

docs/              数据 schema、评测报告、回测报告、协议取舍、部署说明
scripts/           build_db / serve / make_demo / check_vision
```
